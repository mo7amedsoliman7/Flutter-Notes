# LSP
> **If `B` is a subtype of `A`, you should be able to use `B` anywhere `A` is expected without breaking the program.** A subclass must honor the contract of its parent: same inputs accepted, same promises kept, no surprise exceptions or weakened behavior.

The classic giveaway: a subclass that throws `UnimplementedError`, ignores a parent method, or forces callers to check `if (x is Child)` before using it.

---
## Example : Payment refunds

### ❌ Violating LSP

```dart
abstract class PaymentMethod {
  Future<void> pay(double amount);
  Future<void> refund(double amount);
}

class CardPayment implements PaymentMethod {
  @override
  Future<void> pay(double amount) async => print('Card charged \$$amount');
  @override
  Future<void> refund(double amount) async => print('Card refunded \$$amount');
}

class CashPayment implements PaymentMethod {
  @override
  Future<void> pay(double amount) async => print('Cash received \$$amount');
  @override
  Future<void> refund(double amount) async =>
      throw UnimplementedError('Cash cannot be refunded');
}

// The caller only knows about PaymentMethod
Future<void> cancelOrder(PaymentMethod method, double amount) async {
  await method.refund(amount); // 💥 crashes when method is CashPayment
}
```

`cancelOrder` is correct for the parent type, but it blows up for one child. That's the LSP violation.
### ✅ Following LSP

```dart
abstract class PaymentMethod {
  Future<void> pay(double amount);
}

abstract class Refundable {
  Future<void> refund(double amount);
}

class CardPayment implements PaymentMethod, Refundable {
  @override
  Future<void> pay(double amount) async => print('Card charged \$$amount');
  @override
  Future<void> refund(double amount) async => print('Card refunded \$$amount');
}

class CashPayment implements PaymentMethod {
  @override
  Future<void> pay(double amount) async => print('Cash received \$$amount');
}

// The type now tells the truth: only refundable methods are accepted
Future<void> cancelOrder(Refundable method, double amount) async {
  await method.refund(amount); // ✅ can't be called with CashPayment
}
```

The compiler now blocks the bug. A mistake becomes a compile error instead of a runtime crash.

## Example 2: Flutter widgets and repositories

### ❌ Violating LSP

```dart
abstract class UserRepository {
  /// Returns the user with this id.
  Future<User> getUser(int id);
}

class RemoteUserRepository implements UserRepository {
  final ApiClient api;
  RemoteUserRepository(this.api);

  @override
  Future<User> getUser(int id) => api.fetchUser(id);
}

class CachedUserRepository implements UserRepository {
  final Map<int, User> _cache = {};

  @override
  Future<User> getUser(int id) async {
    final user = _cache[id];
    if (user == null) throw Exception('Not in cache'); // ❌ parent never threatened this
    return user;
  }
}

class ProfileCubit extends Cubit<ProfileState> {
  ProfileCubit(this._repo) : super(ProfileLoading());
  final UserRepository _repo;

  Future<void> load(int id) async {
    final user = await _repo.getUser(id);
    emit(ProfileLoaded(user));
  }
}
```

`ProfileCubit` works in production with `RemoteUserRepository`. Swap in `CachedUserRepository` (say, for offline mode) and it crashes on the first cache miss. The cubit would need to know which repository it got, which is exactly what LSP forbids.

### ✅ Following LSP

```dart
class CachedUserRepository implements UserRepository {
  CachedUserRepository(this._remote);

  final UserRepository _remote;
  final Map<int, User> _cache = {};

  @override
  Future<User> getUser(int id) async {
    final cached = _cache[id];
    if (cached != null) return cached;

    final user = await _remote.getUser(id); // falls back, keeps the promise
    return _cache[id] = user;
  }
}
```

Now `ProfileCubit` doesn't care which implementation it gets, and testing is easy:

```dart
class FakeUserRepository implements UserRepository {
  @override
  Future<User> getUser(int id) async => User(id: id, name: 'Test');
}

final cubit = ProfileCubit(FakeUserRepository()); // same contract, no surprises
```

## The rules of a valid subtype

| Rule                                    | Meaning                                                                          |
| --------------------------------------- | -------------------------------------------------------------------------------- |
| **Preconditions can't be strengthened** | Child must accept at least what the parent accepts                               |
| **Postconditions can't be weakened**    | Child must deliver at least what the parent promises                             |
| **No new exceptions**                   | Don't throw errors the parent never threatened                                   |
| **Invariants preserved**                | Don't break rules the parent guarantees (e.g., `width` and `height` independent) |

## Red flags
- `throw UnimplementedError()` or `UnsupportedError()` in an override
- Empty overrides that silently do nothing
- `if (obj is SpecificChild)` checks in code that takes the parent type
- Documentation saying "don't call this on subclass X"

## Quick self-check

Ask: _"Can I replace the parent with this child anywhere, without the caller needing to know?"_

- Yes → ✅
- No, callers must special-case it → ❌

## Relation to the other principles

LSP supports OCP. You can only extend safely by adding new subclasses if those subclasses actually behave like the base type. Break LSP, and your "open for extension" design becomes a minefield.
