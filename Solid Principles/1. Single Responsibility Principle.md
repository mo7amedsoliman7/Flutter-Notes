#  SRP 
> **A class should have only one reason to change.**

Each class, widget, or function should own **one job**. Only one kind of change (a UI redesign, a new business rule, or an API change) should force you to edit it.

---
## ❌ Violating SRP

In Flutter, this shows up constantly: one widget or class doing everything.

```dart
class UserProfileScreen extends StatefulWidget {
  const UserProfileScreen({super.key});

  @override
  State<UserProfileScreen> createState() => _UserProfileScreenState();
}

class _UserProfileScreenState extends State<UserProfileScreen> {
  User? user;

  Future<void> loadUser() async {
    // 1. Networking
    final response =
        await http.get(Uri.parse('https://api.example.com/user/1'));

    // 2. Parsing
    final json = jsonDecode(response.body);

    // 3. Validation / business logic
    if (json['email'] == null || !json['email'].contains('@')) {
      throw Exception('Invalid email');
    }

    // 4. State update
    setState(() => user = User.fromJson(json));
  }

  @override
  Widget build(BuildContext context) {
    // 5. UI
    return Text(user?.name ?? 'Loading...');
  }
}
```
### What's wrong?
This one class changes if:

|Change|Why the class must be edited|
|---|---|
|The API URL changes|Networking lives here|
|The JSON shape changes|Parsing lives here|
|Validation rules change|Business logic lives here|
|The UI changes|Rendering lives here|

That's **four reasons to change**, so it breaks SRP.

---

## ✅ Following SRP

Split each responsibility into its own class.
### 1. Data / networking only

```dart
class UserRepository {
  final http.Client client;
  UserRepository(this.client);

  Future<User> fetchUser(int id) async {
    final response =
        await client.get(Uri.parse('https://api.example.com/user/$id'));
    return User.fromJson(jsonDecode(response.body));
  }
}
```
### 2. Business rules only

```dart
class UserValidator {
  bool isValid(User user) => user.email.contains('@');
}
```
### 3. State management only

```dart
class UserCubit extends Cubit<UserState> {
  final UserRepository repository;
  final UserValidator validator;

  UserCubit(this.repository, this.validator) : super(UserInitial());

  Future<void> loadUser(int id) async {
    emit(UserLoading());
    final user = await repository.fetchUser(id);

    validator.isValid(user)
        ? emit(UserLoaded(user))
        : emit(UserError('Invalid email'));
  }
}
```
### 4. UI only

```dart
class UserProfileScreen extends StatelessWidget {
  const UserProfileScreen({super.key});

  @override
  Widget build(BuildContext context) {
    return BlocBuilder<UserCubit, UserState>(
      builder: (context, state) {
        if (state is UserLoaded) return Text(state.user.name);
        return const CircularProgressIndicator();
      },
    );
  }
}
```

Now each piece has **exactly one reason to change**.

---
## 🎯 Why it matters

- **Easier testing:** unit test `UserValidator` without a network or a widget tree.
- **Easier maintenance:** a UI redesign never risks breaking your API logic.
- **Reusability:** `UserRepository` can serve many screens.
- **Fewer merge conflicts:** teammates work on different files.

---
## ✅ Quick self-check

Ask yourself: _"Can I describe this class in one sentence without using 'and'?"_

|Description|Verdict|
|---|---|
|"Fetches users from the API"|✅|
|"Fetches users **and** validates them **and** renders them"|❌|

---
## ⚠️ Common pitfall

SRP doesn't mean "one method per class." It means **one responsibility**, which can involve several closely related methods.

Don't over-split into dozens of tiny classes either. Split along **real axes of change**.

---
## 📌 TL;DR

| Layer               | Responsibility         | Changes when…                 |
| ------------------- | ---------------------- | ----------------------------- |
| `UserRepository`    | Networking and parsing | API URL or JSON shape changes |
| `UserValidator`     | Business rules         | Validation rules change       |
| `UserCubit`         | State management       | Screen flow or states change  |
| `UserProfileScreen` | UI                     | The design changes            |
