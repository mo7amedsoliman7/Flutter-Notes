#  DIP

> **High-level modules should not depend on low-level modules. Both should depend on abstractions.** Your business logic (cubits, use cases, services) shouldn't know _which_ HTTP client, database, or storage it uses. It should only know an interface, and the concrete implementation gets handed in from outside.

The giveaway: a class that creates its own dependencies with `new`-style calls like `http.Client()`, `SharedPreferences.getInstance()`, or `FirebaseAuth.instance` inside its methods.

## ❌ Violating DIP

### Example 1: A cubit tied to a concrete API

```dart
class UserCubit extends Cubit<UserState> {
  UserCubit() : super(UserInitial());

  // High-level logic creates and controls a low-level detail
  final _client = http.Client();

  Future<void> loadUser(int id) async {
    emit(UserLoading());
    final res = await _client.get(Uri.parse('https://api.example.com/user/$id'));
    emit(UserLoaded(User.fromJson(jsonDecode(res.body))));
  }
}
```

Problems:

- You can't test `UserCubit` without a real network.
- Switching from `http` to `dio` means editing the cubit.
- The cubit (high-level) depends on `http` (low-level).

## ✅ Following DIP

```dart
// 1. Abstraction, owned by the high-level layer
abstract class UserRepository {
  Future<User> getUser(int id);
}

// 2. Low-level detail depends on the abstraction
class ApiUserRepository implements UserRepository {
  final http.Client client;
  ApiUserRepository(this.client);

  @override
  Future<User> getUser(int id) async {
    final res = await client.get(Uri.parse('https://api.example.com/user/$id'));
    return User.fromJson(jsonDecode(res.body));
  }
}

// 3. High-level logic depends only on the abstraction
class UserCubit extends Cubit<UserState> {
  final UserRepository repository;
  UserCubit(this.repository) : super(UserInitial());

  Future<void> loadUser(int id) async {
    emit(UserLoading());
    emit(UserLoaded(await repository.getUser(id)));
  }
}

// 4. Wiring happens at the edge of the app
final cubit = UserCubit(ApiUserRepository(http.Client()));
```

The arrow of dependency is now **inverted**: instead of `Cubit → http`, both point to the `UserRepository` interface.

```
Before:  UserCubit ───────────▶ http.Client

After:   UserCubit ──▶ UserRepository ◀── ApiUserRepository ──▶ http.Client
```

## Example 2: Testing becomes trivial

```dart
class FakeUserRepository implements UserRepository {
  @override
  Future<User> getUser(int id) async => User(id: id, name: 'Test User');
}

void main() {
  blocTest<UserCubit, UserState>(
    'emits loaded state',
    build: () => UserCubit(FakeUserRepository()),
    act: (cubit) => cubit.loadUser(1),
    expect: () => [isA<UserLoading>(), isA<UserLoaded>()],
  );
}
```

No network, no mocking library, no waiting.

## Example 3: Local storage

### ❌ Violating DIP

```dart
class ThemeService {
  Future<bool> isDark() async {
    final prefs = await SharedPreferences.getInstance(); // hard-coded detail
    return prefs.getBool('dark') ?? false;
  }
}
```

### ✅ Following DIP

```dart
abstract class LocalStorage {
  Future<bool?> getBool(String key);
  Future<void> setBool(String key, bool value);
}

class PrefsStorage implements LocalStorage {
  @override
  Future<bool?> getBool(String key) async =>
      (await SharedPreferences.getInstance()).getBool(key);
  @override
  Future<void> setBool(String key, bool value) async =>
      (await SharedPreferences.getInstance()).setBool(key, value);
}

class HiveStorage implements LocalStorage { /* ... */ }

class ThemeService {
  final LocalStorage storage;
  ThemeService(this.storage);

  Future<bool> isDark() async => await storage.getBool('dark') ?? false;
}
```

Moving from `SharedPreferences` to Hive means writing `HiveStorage` and changing one line at the wiring point.

## Example 4: Dependency Injection with `get_it`

DIP is the _principle_; **Dependency Injection (DI)** is the technique to apply it. In Flutter, `get_it` is the common tool:

```dart
final getIt = GetIt.instance;

void setupDependencies() {
  getIt.registerLazySingleton<http.Client>(() => http.Client());

  // Register the concrete class under the abstract type
  getIt.registerLazySingleton<UserRepository>(
    () => ApiUserRepository(getIt()),
  );

  getIt.registerFactory(() => UserCubit(getIt()));
}

void main() {
  setupDependencies();
  runApp(const MyApp());
}
```

```dart
BlocProvider(
  create: (_) => getIt<UserCubit>(),
  child: const UserScreen(),
)
```

To swap implementations (for example in tests or a different flavor), you change only the registration line.

## DIP vs. DI vs. IoC

|Term|What it is|
|---|---|
|**DIP**|The principle: depend on abstractions|
|**DI**|A technique: pass dependencies in (constructor, setter, container)|
|**IoC**|The broader idea: something else creates and controls your objects|

DI is the _how_, DIP is the _why_. You can follow DIP with plain constructor parameters and no library at all.

## Why it matters

- **Testability:** swap real dependencies for fakes.
- **Flexibility:** change `http` to `dio`, or REST to GraphQL, in one place.
- **Parallel work:** one dev builds the UI against a fake repository while another builds the real API.
- **Clean Architecture:** this is the rule that makes the domain layer independent of data and UI layers.

## Common pitfalls

- **Don't abstract everything.** Wrapping `Duration` or `List` in interfaces is pointless. Abstract things that do I/O or are likely to change: network, storage, platform APIs, third-party SDKs.
- **Constructor injection beats service locators.** Calling `getIt<Repo>()` deep inside a class hides dependencies and brings back the original problem. Resolve at the composition root and pass them in.
- **Interface placement matters.** The abstraction belongs with the high-level code (domain layer) that _uses_ it, not with the implementation.

## Quick self-check

Ask: _"Does this class create its own dependencies, or receive them?"_

- Receives an abstraction → ✅
- Calls `Something.instance`, `Something()` for a service, or `getInstance()` inside → ❌

|Principle|One-line summary|Flutter example|

|**S**RP|One reason to change|Split UI, cubit, repository|
|**O**CP|Extend, don't edit|`PaymentMethod` strategies, validator rules|

|**I**SP|Small, focused interfaces|`Readable<T>` vs `Writable<T>`|
