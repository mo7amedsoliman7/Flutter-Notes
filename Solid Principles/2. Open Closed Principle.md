# OCP
> **Software entities (classes, widgets, functions) should be open for extension but closed for modification.** You should be able to add new behavior by writing new code, not by editing code that already works and is already tested.

The usual giveaway of an OCP violation is a growing `if/else` or `switch` chain that you must edit every time a new case appears.

---
## ❌ Violating OCP

### Example 1: Payment methods

```dart
class PaymentProcessor {
  void pay(String method, double amount) {
    if (method == 'card') {
      print('Paying $amount with credit card');
    } else if (method == 'paypal') {
      print('Paying $amount with PayPal');
    } else if (method == 'vodafone_cash') {
      print('Paying $amount with Vodafone Cash');
    }
    // Every new payment method = edit this class again
  }
}
```

Adding Apple Pay means modifying `PaymentProcessor`, which risks breaking the methods that already work.

## ✅ Following OCP

Depend on an abstraction, and extend by adding new classes:

```dart
abstract class PaymentMethod {
  void pay(double amount);
}

class CardPayment implements PaymentMethod {
  @override
  void pay(double amount) => print('Paying $amount with credit card');
}

class PayPalPayment implements PaymentMethod {
  @override
  void pay(double amount) => print('Paying $amount with PayPal');
}

class VodafoneCashPayment implements PaymentMethod {
  @override
  void pay(double amount) => print('Paying $amount with Vodafone Cash');
}

// Closed for modification: never changes again
class PaymentProcessor {
  void pay(PaymentMethod method, double amount) => method.pay(amount);
}
```

To add Apple Pay, you create `ApplePayPayment` and touch nothing else.

## Why it matters

- **Less regression risk:** working, tested code stays untouched.
- **Easier testing:** each new class gets its own small test.
- **Parallel work:** teammates add new classes without conflicts.
- **Cleaner code:** no giant `switch` blocks.

## Common pitfalls

- **Don't over-abstract early.** If you have only one payment method and no sign of more, an interface is premature. A good rule: apply OCP when you see the **second or third** variation appear.
- **Not everything can be closed.** You must guess which axis will change (payment types? discounts?) and abstract that one. Trying to protect against every change leads to over-engineering.
- **Enums with `switch` are fine** when the set is truly fixed (e.g., `Brightness.light/dark`). In Dart 3, a `sealed` class with exhaustive `switch` is a good alternative when you _want_ the compiler to force you to handle every case.

## Quick self-check

Ask: _"When a new type or case appears, do I add code, or edit existing code?"_

- Add a new class → ✅
- Edit an existing `if/else` chain → ❌
